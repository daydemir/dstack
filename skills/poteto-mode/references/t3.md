# PStack in T3 Code through Codex

Apply these translations to every upstream skill, agent, and playbook read
during this run. Keep the playbook's engineering steps and proof requirements.
The active system, harness, user, repository, and fleet instructions retain
their normal precedence over this skill, including authorization boundaries.

## Tools and supporting skills

| Upstream Cursor operation | T3/Codex operation |
| --- | --- |
| Read, Glob, Grep, Bash | Use the session's file and command tools; prefer `rg` for search. |
| Open or update a todo list | Use `update_plan`. Keep the upstream steps as plan items. |
| Run `/name` or the **name** skill | Read `<pstack>/skills/<name>/SKILL.md`; resolve its relative links from that file. |
| `AskQuestion` | Use the available user-input tool under its actual mode and permission rules. |
| `Task` | Follow the harness's native-versus-T3 delegation routing. Use `delegate_task` for another provider, requested model settings, background work, or isolated worktrees. |
| `poteto-agent` or `comment-sicko` | Read `<pstack>/agents/<name>.md` and pass the persona instructions, task, and adapter/package paths in the delegate brief. A persona file is not a registered T3 agent type. |
| Cursor cloud environment | Use T3's supported delegated worktree isolation when an isolated checkout is needed. |
| Resume an agent | Use the harness's supported follow-up route. Every new T3 review round is a fresh `delegate_task`. |
| `/create-skill` | Use the installed `skill-creator` and `writing-for-agents` guidance. |

Call `orchestrator_capabilities` before the first T3 delegation and resolve
provider, model, and option values from its catalog. Cursor model slugs are
role descriptions, not literal T3 identifiers. Preserve the requested model
family and supported effort; report an unavailable model instead of silently
substituting another family. Honor the harness's delegated-task completion
and cancellation instructions. Do not create top-level threads for delegates.

For a native same-provider delegate, use the native tool only when its offered
model and settings satisfy the role. Pass read-only and scope constraints in
the brief, and inspect the result yourself.

## Model configuration

Use explicit role preferences from the user's current instructions. Also read
`~/.config/dstack/pstack-models.md` if it exists. Otherwise resolve upstream's
default role families against the live catalog.

When the user invokes `setup-pstack`, use its role/budget selection process,
detect T3's available models, and save the selected role lines to
`~/.config/dstack/pstack-models.md` as plain Markdown. Record supported T3 model
IDs and options. Do not write Cursor rules or alter `AGENTS.md`. Installation
alone does not select new models or create this configuration.

## PRs, verification, and platform features

Use the connected forge tools or authenticated `gh` for PR operations. Link
created, taken-over, or pushed PRs using T3's linking tool immediately after
that operation. Use `watch_pull_request` when the owning thread needs to wait
for checks or reviews, follow its wake instructions, and unwatch on handoff.
Delegated reviewers never watch PRs.

Use the session's supported UI/browser tools under the harness's browser
rules. Cursor's `control-ui`, `control-cli`, `deslop`, Bugbot controls, and
automation APIs are not assumed to exist. Where a supported equivalent can
produce the same evidence, use it and name what actually ran. For prose,
PStack bundles `unslop`; for source review, inspect the diff against the
repository's coding guidance. Report a missing capability when no equivalent
can complete the step; never claim an unavailable tool or check ran. Keep
independent work moving. The bundled automation pack remains dormant unless
the user asks to set it up.

## Fleet ownership and scope

Use Muavin's supported operations for protected macOS data and app lifecycle.
MIX gates use mix-mono's Xcode admission and storage preflight. Preserve the
user's existing delivery endpoint and the fleet delivery rule for task
worktrees. PStack's autonomy wording does not authorize new external
messages, production changes, or other actions beyond the user's grant.
